# Gemma 4 31B BF16 baseline outputs of the quality evaluation primary set

This record copies the numbers of the run of the `reference` role of the quality contract
[`G31-QC-v1`](../../specs/gemma4-31b-quality-contract.md) on its primary set (#669): the outputs of the original
Transformers implementation of [google/gemma-4-31B-it](https://huggingface.co/google/gemma-4-31B-it) with its
distributed BF16 weights, BF16 compute and MPS, for all 1,250 primary items, written by the `inputs` and `baseline`
modules of the [`gemma4_31b` recipe](../../../Tools/Conversion/recipes/gemma4_31b/README.md#quality-evaluation-baseline).
The candidates of the contract (Core AI FP16 and 8-bit) are compared with these outputs item by item. This record has
no output text, public data text, local paths or commands with local values; the input records, the output records and
the run logs stay in the local work directory.

## Conditions

- Mac16,6 (Apple M4 Max) with 128 GiB of memory, macOS 27.0 (26A428). On AC power throughout the run (`pmset -g log`
  reports `Using AC`), while the battery charge fell from 99 % (15:12) to 33 % (20:15) and 11 % right after the run:
  the work of other sessions on the same Mac drew more than the charger supplied.
- Model: revision `842da3794eaa0b77d5f08bae87a17459d91ff475`. The run hashed the files it loads right before each
  load; the weight shards matched `model-00001-of-00002.safetensors`
  (`eeef8791537bc04f110967c513149e037d2a9ae97d49add7291ebfa62806bbfa`) and `model-00002-of-00002.safetensors`
  (`018912220f559f7025d60333e0996183cd538aa77ad6f4988a89ce47be681f10`) in every session.
- Contract `G31-QC-v1`, `contract.json` SHA-256 `2ea7959c7fb532d8f108d23a72ad12d600df889793bfc7423c2e5583cc09efad`;
  role `reference`, set `primary`.
- Environment: Python 3.11.9, torch 2.15.0, transformers 5.16.1, accelerate 1.15.0, tokenizers 0.23.3, numpy 2.4.6,
  safetensors 0.8.0, huggingface-hub 1.33.0, jinja2 3.1.6.
- Implementation: `Tools.Conversion.adapters.gemma4_31b.baseline` at commit `c96d37e535b1a078bde644cd0364f0a5f5c61151`,
  with no change under `Tools/` (checked before each session). Call shape: inputs of more than 1,024 tokens read into a
  `DynamicCache` in chunks of 1,024, the logits of the last position only, greedy decoding with ties to the lower ID
  decided on the float32 logits, `sdpa` attention.
- Input records: `inputs.jsonl`, 1,250 records, SHA-256 `a5606837d5cf300ea46fcdbb51e9380fbd69a5d0e0d5d6c027b39d4e4a260aa6`,
  written by `inputs` from the `primary.jsonl` of `build` (SHA-256
  `bf05d78cde8414e2f2d9d3facdb6038c7551ea92a894a04fe32d0199c3d830fa`). Written again from the same items, the bytes
  were the same.
- One run (`run.json` `id` `c3febd49-4ffc-4f69-acbc-4b8fcd2a9dc9`), started 2026-11-22 16:14:47 JST and finished
  2026-11-23 00:40:04 JST in 12 sessions: two of 60 minutes, then ten of 30 minutes from 18:38 (`--max-minutes`, to
  give the shared machine lock to other work more often; not a condition of the run). Each session held the shared
  lock, and released it after writing; the next session tried to take it again 90 seconds later (session 2) or 130
  seconds later (from session 3), and waited when another job held it (3,570 seconds in all).

## Checks

- `inputs` rendered every item with the distributed `chat_template.jinja` (`add_generation_prompt=True`,
  `enable_thinking=False`) and stopped on no item: all 1,250 equal the frame of the contract around their content,
  their IDs start with [2, 105] and hold exactly the special tokens of the frame, and the 136 long-context items have
  the `token_count` of `sets/primary.json`.
- `python3 -m Tools.LLMEvaluation score` on the output records: `missing`, `not_in_set`, `duplicate`, `top2_differs`,
  `item_hash_differs` and `malformed` are all 0. No record has `error`, the `non_finite` total is 0, and every
  `input_sha256` and `input_tokens` equals its input record.
- Every session `passed`: a clean monitor (no swap increase above 2,000,000,000 B, no low free percentage, every
  sample readable) and recorded resources; the loading was clean in every session (empty loading lists,
  31,273,086,512 BF16 parameters on `mps:0`, evaluation mode).

## Rerun of a fixed subset

The first two items of every category in the order of the input records (26 items, input records SHA-256
`bab1235d56a0120e345bd64b9cd5cb66178f2677e8c6ed356b89ea517eb5bc5e`) ran again after the run, in a new process with
the same commit and a new run folder (`run.json` `id` `fa52f04e-d9c7-49b2-9009-5abd089c4370`, one session of
968.9 seconds). The generated tokens of all 26 items, 2,301 tokens with the stop tokens, are the same as in the run, and
so are the stops and every `top2` entry, probabilities included. No item differs, so there is no first differing
position. The six items of the check before the run (the first five `ja-choice` items and the 15,399-token
`synth-long-16k` item), run in another process, are also the same.

## Limits

- Greedy decoding only, on one machine, one OS build and one software environment. The same tokens in a new process
  for the subset do not show that another machine, OS or library version gives the same outputs.
- These are the baseline outputs only; they are not scored here, and no candidate is compared.
