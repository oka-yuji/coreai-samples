## Verified publication scope

The shipped API policy is limited to the independently reconciled January 2025 data for the twenty demo zones, at dataset `irx2-vgm4` revision `2026-10-01T16:57:47.000Z`. Its half-open data interval is January 1 00:00 through February 1 00:00 New York. A full 1,008-bin history allows forecast origins from January 22 00:00 through February 1 00:00, inclusive. The [range evidence](verified-range.json) is not a claim of support for every annual dataset in the catalog.

The January Parquet alone differed from the API at nine month-end cells. The February Parquet contains thirty January pickups, ten in the selected zones. Adding those ten resolves all 29,760 counts. Both source hashes and the first failed comparison are retained. `Tools/NYC/verify_api_reference.py` independently reproduces the shipped reference from both source files; the production client also retrieved and validated all 29,760 January values in two windows.

Every returned count in the approved range is compared with that reference. A missing positive count is an error; a known zero remains zero. A listed dataset with an unknown revision or outside interval produces `unverified` missing values, while an unlisted year remains `unpublished`. Histories containing unverified intervals cannot run the model. Mixed actual windows retain their missing suffix and cannot advance the input across it. Metadata is checked before and after acquisition. Cache and snapshot identities bind the verification policy and reference hash; older broad-range cache entries do not grant access.

The earlier metadata-only contract and its native/GUI observations are retained in [pre-range results](pre-range-results.json). Annual metadata is useful for identity and schema validation, but is not a sufficient completion watermark for zero filling. Other periods need separate source reconciliation before inclusion.

## Contract corrections and failure evidence

- SDK27.2's ISO8601 parser accepted a trailing suffix/newline and normalized impossible dates and hour 24. Four catalog-entry regression cases failed before the fix. Supported UTC seconds/milliseconds must now round-trip to the complete input string; valid revisions and original-response replay still pass.
- The original annual guard rejected the captured 2019, 2020 and 2021 metadata because publication dates can precede year end, and 2021 uses `As needed`. The first repair at `05f8363` required a matching catalog revision and a data update after the annual period closed; it accepted the special frequency only with the official historical-publication/corrections declaration. At that revision, nine pinned captures passed, while zero/future publication dates, an unproven frequency and rows last updated before year end were rejected. The verified-range repair subsequently removed the annual-end update restriction. Current metadata checks retain identity, owner, provenance, publication state, column types, valid dates and revision consistency; metadata updated during its year can parse, but only the independently verified policy can authorize observed counts or a usable history. The earlier metadata-only scope is historical evidence, not the current completion rule or a numerical completeness audit of every year.
- Injected abandoned UUID staging files survived the former cache pruning. Recovery, write, rename and pruning now hold the same exclusive lock, preserving other active writers that use this implementation. The regression keeps unrelated files. The 32-window/64-MiB limit applies to committed cache files after a completed save; an active staging file adds temporary space. Actual process termination or power loss was not exercised.
- The first parent CPU run after adding the bundled reference failed twelve default-profile cases. The source and embedded reference bytes were then checked against the same hash; rebuilding the test target and adding an explicit source/bundle comparison passed, including a separate bundled-first check. The exact cause of that initial resource failure was not established and is not described as a proven production defect.
- A preparation-only actuals request received HTTP503 once, then succeeded on a new attempt and matched all 80 pinned two-hour counts. The failure was retained separately from the successful retry. It was not labelled unpublished or replaced with a cached forecast.
