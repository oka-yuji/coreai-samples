# Shared model library contracts

`ModelLibraryFeature` provides the catalog and state machine for model-first demo navigation. It does not download files, create inference services, or change the existing app entry points. The iOS integration consumes these contracts separately.

## Catalog

`ModelDemoDefinition` requires an ID, title, symbol name, summary, explanation, platform set, and visibility. `DemoDescriptor` is the value implementation. A `LibraryModel` declares one or more converted artifacts (variants), its default artifact, and its explicit `ModelDemoLink` entries. Artifact IDs are unique across the catalog, so several models can link the same demo ID without sharing installations.

A `ModelArtifact` has a display title, contract, platform set, visibility, optional distribution, optional upstream source, and the complete set of files a device needs. `ModelDownload` identifies an owner/repository, a lowercase 40-character revision, and a bundle-relative root. `ModelArtifactFile` lists a relative path, byte count, and lowercase SHA-256. The catalog rejects empty, absolute, `.` or `..` path components, malformed checksums, duplicate paths, and a configured distribution without files. An unconfigured artifact may omit files. A missing distribution or an unpinned revision cannot become executable through inspection of pre-existing files.

The distribution revision pins the converted repository. The upstream revision (`ModelUpstream`) identifies the source model. They are separate values and are never compared with each other.

Visibility intersects the model, artifact, demo, and link publication with their platform sets. A model is listed while at least one variant is visible; `ModelSection.artifacts` holds those variants. Search returns model sections, including when only a demo title matches.

## State and identity

`ModelLibraryState` receives a `LibraryEnvironment`: platform, audience, the demo IDs whose adapters are connected, and capability states (`available`, `undetermined`, `denied`, `unsupported`). A capability absent from the environment is `undetermined`. Pure logic never reads the device, OS, or permission state. The application also injects the state `owner`.

Requests, sessions, and stop operations use `LibraryTicket` (owner and number). A ticket from another owner, such as another scene or a previous launch, never matches, even with the same number.

Installations are keyed by artifact ID, so variants of one model have independent states. `selectedArtifacts` starts with each model's default. `selectedArtifact(for:)` returns nil when the selection is not visible. It never substitutes another variant, and `access(to:)` then returns `.unavailable` until the user selects a visible one. `selectArtifact` changes the selection immediately when that model has no demo session. Otherwise it stops the session through the same barrier as navigation and applies the new variant after `demoStopped`.

`ValidatedModelResource` carries the model and artifact IDs, contract, distribution revision, upstream revision, directory, and size. `matches(model:artifact:)` requires all identity fields to equal the catalog entry. `ModelArtifactIdentity` (model, artifact, contract, distribution revision) is available from the resource and from `ModelDemoSession.identity` so that results can record which variant produced them.

## Execution

Opening an unavailable model/demo combination is rejected. A supported demo whose artifact is missing, or whose adapter is not connected, only selects its explanation (`.preview`). `isConnected(_:)` lets the UI show that execution is not connected.

`permits(_:selection:)` is the execution gate. The active session ticket, connected adapter, selected artifact, validated resource, catalog eligibility, pinned distribution, and required capabilities must all hold. A `denied` or `unsupported` required capability blocks execution. `available` and `undetermined` allow the demo's explicit Start to request permission before any capture, recording, or inference. Optional capabilities never block execution. `capabilityChanged` only updates the environment and never removes a model or demo from the list.

Completing an inspection, transfer, or variant change does not issue an inference effect. `ValidatedModelResource` is the boundary value returned by the validator. Construct it only after checking the actual bundle and its identity. Matching this value in pure logic is not a substitute for file and checksum validation in the I/O implementation.

## Effect ownership

The existing generic `Store` owns tasks. The application supplies one runner that owns the actual transfer and demo resources. Resource actions carry the artifact ID and request ticket, and effects carry the model and artifact. The runner must preserve these values when sending progress, completion, or failure.

- `inspect` examines existing resources without loading an inference model. A refresh skips the artifact used by the active session.
- `download` writes an incomplete transfer to a staging location. `downloaded` requests a distinct validation operation; only `validated` can make the resource ready.
- Cancelling a resource emits both a cancellation command and `stopTransfer`. Cancellation is cooperative: `transferStopped` must arrive only after the previous I/O has terminated and its staging resources are no longer being modified. Cancellation acknowledgement is an infallible join contract, not a success report for the download. The state rejects late completion and prevents another transfer while stopping.
- `delete` is rejected while a demo of the same model owns a session or while a stop is pending. A deletion failure invalidates the cached availability until a subsequent inspection verifies the remaining files.
- `stopDemo` carries both the old session and a unique stop ticket. The runner must finish inference, camera/audio cleanup, and resource release before sending the matching `demoStopped`. `demoStopFailed` keeps navigation, execution, deletion, and variant changes blocked; `retryDemoStop` uses a new ticket. An old stop result cannot complete a later attempt.

Demo data remains owned by its feature. The library retains definitions, the selected destination, and the selected variants across transfer and stop failures. It never deletes input, history, or generated results. Keeping those values when a demo runner releases runtime resources is the integration's responsibility.

## Storage

`ModelLibraryStorage` provides `ManagedModelStore`, an actor that owns the managed model area. The application passes `Application Support/<bundle ID>/ModelLibrary` as the root; `IOSModelLibraryAssembly` connects it to the iOS app (#192). Hashing, copying, and enumeration run on the actor, never on the main actor, and check cancellation between files and between 1 MiB reads.

| Path under the root | Contents |
|---|---|
| `artifacts/<artifact ID>/<distribution revision>/` | Verified bundles, laid out by the definition's relative file paths. Revisions are separate directories. |
| `staging/<artifact ID>/<distribution revision>/` | Incomplete files of that revision. `stagingDirectory(for:artifact:)` always returns this directory, creating it when needed and keeping the files already in it. One transfer per artifact runs at a time. |
| `trash/<UUID>` | The store's own holding area for a replaced or deleted bundle. The next promotion or deletion empties it. |
| `ledger.json` | Format 1. One entry per artifact and revision: model ID, artifact ID, contract, distribution revision, upstream revision, size, installation time, and generation. It is written to a temporary file and renamed atomically. |

The root itself may be a symbolic link. Below it, an existing `artifacts` or `staging` folder, artifact folder, or revision folder that is a symbolic link is rejected with `symbolicLink`, and an existing one must resolve inside the root (`pathEscape` otherwise). Every operation checks this before reading, moving, or deleting anything.

`inspect(model:artifact:)` returns `.missing` without reading files when the distribution is absent or unpinned. Otherwise it compares the artifact directory with the pinned definition, whether or not the ledger lists it. Every listed file must be a regular file with the listed size and SHA-256. Any other file or directory, a symbolic link, a folder that cannot be listed (`unreadableDirectory`), and an empty, absolute, `.` or `..` path component are rejected. Folders are listed with `readdir`, so hidden files, including AppleDouble `._` names that `FileManager` enumeration omits, count as unlisted files. The contract check follows:

- `gliner-gl4-*`: the definition includes `tokenizer/tokenizer.json` or `tokenizer.json`, `GLiNERAsset(directory:)` succeeds, and the `model` and `revision` in `contract.json` equal the upstream.
- `embeddinggemma2-fp16-safe-s128-v70` and `embeddinggemma2-int4-int8-ptq-s128-v70`: `EmbeddingBundle(directory:)` succeeds with the matching precision profile, and the manifest revision equals the upstream revision.
- Any other contract is rejected.

A passing bundle updates its ledger entry and returns `.ready`. The resource's `revision` is the distribution revision, and `upstreamRevision` is the upstream revision. A failing bundle returns `.invalid` with the original error (`ManagedModelStoreError`, `GLiNERAssetError`, `EmbeddingError`, or a file system error), including when only the ledger lists it. A ledger entry alone never makes a resource ready. Inspection and promotion ignore a ledger that cannot be decoded and replace it on their next write; deletion refuses it with `ledgerCorrupted`. Inspection does not connect to the distribution or load Core AI. Cancellation is thrown, not reported as an invalid bundle.

`promote(staging:model:artifact:)` accepts only the revision's staging directory or a directory below it. It runs the inspection checks, so an unlisted file such as a leftover partial download is rejected. It then moves an existing bundle of the same revision to the trash, moves the staging directory into place, records a new generation, and removes the trash and anything left in the staging directory. If a move or the ledger write fails, the directory returns to staging, the previous bundle returns from the trash, and the error is thrown. Other revisions are never touched. A process exit between the two moves leaves that revision missing rather than ready; its previous bundle remains in the trash until the next promotion or deletion removes it.

`migrate(candidates:model:artifact:)` requires every listed file of a candidate folder to be a regular file with the listed size and SHA-256, and rejects a symbolic link anywhere in the folder. Unlisted files, such as `SHA256SUMS`, verification records, another `.aimodel`, or `.DS_Store`, are ignored and never copied. A candidate that resolves to the root or a location inside it is `undetermined` (`pathEscape`) and is not read or changed. A candidate with a missing or changed file, a symbolic link, or an unsafe path is `undetermined` and is not registered. For a matching candidate, a capacity check runs first; the staging directory is then emptied, only the listed files are copied (never moved), and the copy is promoted, so the contract checks run on exactly the listed files. Failures are reported as `failed` and remove the copy; a capacity failure leaves the staging directory unchanged. Once the artifact is ready, the remaining candidates and later runs are `skipped`, so repeated runs create no duplicates. Originals are never modified or deleted, and `promote` refuses a folder outside the staging area.

`lease(identity:owner:)` returns a `ResourceLease`. `release()` is idempotent, and `activeLeases(identity:)` counts the remaining leases. Deleting or promoting a leased identity fails with `inUse`. `delete(identity:)` also requires a ledger entry with the same model, artifact, contract, and distribution revision (`notInstalled` otherwise). It removes the ledger entry, moves the bundle to the trash and deletes it, deletes that revision's staging area, and returns the bytes of those files, which `deletionSize(identity:)` reports beforehand. A failure after the ledger entry is removed is thrown. The next inspection verifies what remains: a moved or partially removed bundle is missing or invalid, and only a complete bundle that still passes every check becomes ready again. Promotion and deletion only change the store's own folders (that revision's bundle, its staging directory, and the trash). They never change the other artifacts recorded in the ledger, originals outside the staging directory, user data such as inputs and saved results, or the Core AI specialization cache.

Every ledger write that registers a bundle receives a larger generation, which never decreases while the process runs. The ledger stores the generation of each entry; leases exist only in memory. `ValidatedModelResource` has no generation field, so `generation(of:)` exposes the recorded value; `ModelLibraryRunner` uses it when it takes a session's lease (see Runtime).

## Transfer

`ModelLibraryTransfer` provides `ArtifactTransfer`, an actor that downloads one artifact into the staging directory returned by `ManagedModelStore.stagingDirectory(for:artifact:)`, and `ModelLibraryResourceRunner`, the main-actor runner for `inspect`, `download`, `validate`, `delete`, and `stopTransfer`. `IOSModelLibraryAssembly` connects both to the iOS app (#192).

The definition is the complete file set. For each listed file, the transfer requests `https://huggingface.co/<repository>/resolve/<revision>/<root>/<path>` with every root and path component percent-encoded, without credentials, cookies, a URL cache, or a query. It never lists the repository through the Hub API, so paging, list completeness, and LFS or Git blob checksums do not apply, and unlisted repository files are never requested. A definition with an unpinned revision, no files, duplicate paths, a path that equals another listed path followed by `.part`, or an empty, absolute, `.` or `..` component is refused before any request.

Before the first request, the transfer removes every staging entry the definition does not list: `.part` files, AppleDouble `._` files, other files and directories, and symbolic links. It lists staging with `subpathsOfDirectory(atPath:)`, because `FileManager` enumeration omits `._` names that the store's `readdir` scan rejects. It recomputes the size and SHA-256 of each listed file already in staging, keeps the matching files, and deletes the others. The available capacity for important usage must cover the remaining bytes (`insufficientSpace` otherwise). At most three files are requested at a time, in definition order. Each response is written to `<path>.part`. A non-2xx status, a size or SHA-256 mismatch, or a transport error fails the transfer with the file path (`http`, `size`, `checksum`, `transport`) and removes the part file. A transport error keeps only the `URLError` code, never the URL. A verified part file is renamed to its path, so a completed transfer leaves exactly the listed files in staging.

Progress is the verified bytes over the definition's total: the reused bytes first, then a value after each verified file. Values only increase; there is no progress within a file. Cancellation stops every request in flight and waits for all of them to return before `CancellationError` is thrown. Verified files stay in staging for the next attempt, and part files are removed.

The runner allows one resource operation per artifact at a time. A request for an artifact whose operation is still running, such as another scene's download, fails with `transfer in progress` and leaves the running operation untouched. The `Store` cancels the operation through the `.cancel(.resource)` command that precedes `stopTransfer`; a cancelled operation sends nothing, even when its work completes after the cancellation. `stopTransfer` waits until the operation with the same ticket has returned, so `transferStopped` follows the end of its requests, hashing, and promotion. A promotion that has already passed verification may still complete after cancellation; the next inspection reports it. Inspection reports `.ready` resources, tries the injected migration candidates once for a missing artifact, and logs an `.invalid` result before reporting it as not installed. A migrated candidate is reported as ready; otherwise the first candidate whose migration failed, such as for lack of space, is reported as an operation failure, and candidates that do not match the definition are ignored. A validation failure is `invalidResource`, except `inUse` (`modelInUse`) and capacity, ledger, and file system errors (`operation`). Transfer failure messages are English and contain only file paths and HTTP status codes; store errors are reported by their case name and file system errors by their localized description. On its own, the resource runner answers `stopDemo` with `demoStopFailed`; `ModelLibraryRunner` answers it before delegating (see Runtime).

## Runtime

`ModelLibraryRuntime` connects demos to the library. Its `ModelLibraryRunner` is the runner of `Store<ModelLibraryFeature>`.

- `ModelDemoAdapter` is the registration boundary for one demo ID. `preview(for:)` draws only from metadata and inputs or results the adapter already holds; it creates no Store, model, camera, or audio work. `content(for:gate:)` returns content only (no navigation stack, vertical scroll view, title, or model picker), bound to the demo Store that the adapter keeps for each model and demo, and attaches the session's validated resource to that Store. `stop(_:)` returns only after the demo's child work has ended, its OS resources have stopped, and its runtime references are released, and throws when it cannot confirm this. A retry must be idempotent. It must finish even when the calling task is cancelled, and it must not cancel a save or share the user has already started. `Store.cancelAll` alone is not a stop.
- `DemoExecutionGate` carries the session and `isPermitted`, which is true only while the library's `permits(_:selection:)` holds for that session and the runner holds the session's verified lease. It is closed until that lease has been taken and checked, and it stays closed for a session whose identity was missing from the ledger. Each adapter checks it in its demo Store's runner immediately before every side effect (loading, inference, fetching, capture, recording, playback, file import) and sends that demo's failure action instead of running the effect when it is false.
- `ModelDemoAdapterRegistry` holds one adapter per demo ID. `connectedDemos` feeds `LibraryEnvironment.connectedDemos`, so every adapter is registered before the library state is created.
- `ModelLibraryRunner` passes `inspect`, `download`, `validate`, `stopTransfer`, and `delete` to `ModelLibraryResourceRunner` and answers `stopDemo` itself. It awaits the adapter's `stop(_:)` and sends `demoStopped` on success or `demoStopFailed` with the error description on failure. A demo without an adapter has nothing to release and is acknowledged. A second stop of the same session while one is running waits for it and receives the same result, so one adapter stop answers both tickets.
- When the host shows a session's content, the runner takes one `ManagedModelStore` lease for that session, owned by the session's ticket owner, and keeps a weak reference to that owner's library store. It then reads `generation(of:)`: when the identity is no longer in the ledger (another owner deleted it before the lease), it releases the lease, keeps the gate closed, and sends `resourceLost(artifactID:session:)` to that library store. A successful stop waits for a lease that is still being taken, releases it, and only then acknowledges, so the same owner can delete the model right after `demoStopped`. A failed stop keeps the lease for the retry. A content appearance that arrives after the session's stop succeeded takes no lease.
- `abandon(owner:)` closes an owner for good: no later content appearance of that owner takes a lease, because an owner ID belongs to one scene and is never reused. It stops every session of the owner that holds or is taking a lease and releases the leases, through the runner's own store, so it completes even after that owner's library store has been released. It sends no acknowledgement; a library store that still exists receives its own `demoStopped` through `suspendDemo`. A session whose stop fails keeps its lease and is recorded as abandoned. The runner tries again after 1, 2, and 4 seconds (the delays are an initializer parameter), and then once more whenever another owner is abandoned, a session prepares its lease, a `stopDemo` starts, or `retryAbandoned()` is called. The app calls `retryAbandoned()` whenever a scene becomes active.
- `ModelLibraryRendering` is the `ModelDemoRendering` of the app. It returns the registered adapter's preview and content. A demo without an adapter shows the description preview (its input label and a disabled action) and, if a session ever reached it, a not-connected message. `actions(entering:capabilities:)` maps scene phases to library actions: `background` suspends, `active` only updates the capability states, and `inactive` (such as a permission dialog) sends nothing.

`suspendDemo` stops the current session through the same barrier as navigation, with the current demo as its destination. After `demoStopped`, the selection is unchanged and a new session may be created for it, but nothing runs until the user starts the demo again. It is ignored without a session and while a stop is pending, so a second close or suspension never replaces the stop in progress.

`resourceLost(artifactID:session:)` is ignored unless it names the current session and that session's artifact. It records the artifact in `pendingLoss` and stops the session through the same barrier with the current demo as its destination; when a stop is already pending, it waits for that stop instead. When `demoStopped` arrives, the artifact's installation is reset to missing before the destination is applied, so no session is created and the demo returns to its description with the download action. A failed stop keeps `pendingLoss` until a retry succeeds. Inputs and results that the adapter keeps are not removed.

`ModelLibraryAssembly` builds the runtime from a list of adapters, a `ManagedModelStore`, an `ArtifactTransfer`, and the migration candidates. It registers every adapter in one `ModelDemoAdapterRegistry` and creates one `ModelLibraryResourceRunner` and one `ModelLibraryRunner`. `makeLibrary(catalog:capabilities:owner:)` then creates a scene's `LibraryEnvironment` (iOS, the registry's connected demos, and the given capability states), its library store, run by that runner, and its `ModelLibraryRendering`, so every adapter is registered before any library state exists.

`IOSModelLibraryAssembly` keeps one `ModelLibraryAssembly` per process, with one `ManagedModelStore` at `Application Support/<bundle ID>/ModelLibrary` and one `ArtifactTransfer`, so the runners, the registry, and the adapters' demo Stores are shared by scenes; the iPhone app has one scene, and owner tickets and leases keep several scenes apart. The process creates that folder the first time it uses the assembly and excludes it from backups (`isExcludedFromBackup`). `IOSModelLibraryAssembly.adapters` lists the five demo adapters: comparison (#193), extraction (#194), inspection (#195), image search (#196), and camera search (#197). `make(catalog:)` stops the app with a precondition failure when their demo IDs differ from the catalog's demos. The migration candidates are the folders directly under Documents that contain `contract.json`, followed by `Documents/embeddinggemma2` and `Documents/embeddinggemma2-int4-int8`; they are listed on the main actor when an artifact is missing. Each scene gets its own owner and library store. It suspends its demo when it moves to the background. When its root view disappears, `close(_:)` sends `suspendDemo` and calls `abandon(owner:)`, so the stop and the lease release finish even if the scene's library store is released first. `enter(_:library:)` maps each scene phase to library actions and, on `active`, retries abandoned stops. `IOSDemoCatalog` has no adopted distribution yet (#188), so no artifact can become ready: no session is created, the adapters' content and work are never reached, and every demo shows its description. Capabilities come from the camera, microphone, and speech recognition authorization states (`restricted` is `denied`, an unknown state is `unsupported`), and the network is `available`. They are read again whenever the scene becomes active; the library never requests a permission.

## Verification boundary

Issue #171 covers the original pure-logic contract. Issue #189 adds variants, file sets, revision identity, tickets, the environment, capabilities, and adapter connection. The tests cover catalog intersections, search ownership, inspection versus execution, identity and revision mismatches, pinned distributions, progress, stale and foreign completions, cancellation, deletion, variant changes, and stop/retry ordering. A shared-demo fixture and a ten-demo fixture use the same registration path. GPU inference and real model distribution are outside these tests.

Issue #190 adds `ModelLibraryStorageTests`, which build small GLiNER and EmbeddingGemma 2 fixtures (both precision profiles) in temporary directories, with definitions pinned to their actual SHA-256 values. They cover acceptance and rejection, interrupted and cancelled operations, capacity and ledger failures, migration, leases, deletion, and external replacement without downloading files or loading models.

Issue #191 adds `ModelLibraryTransferTests`. A fake transport serves content, HTTP status codes, disconnections, and requests held until the test releases them, and records request order and concurrency. The tests combine the feature, the runner, the fake transport, and a `ManagedModelStore` in a temporary directory through `Store<ModelLibraryFeature>`. They cover the pinned request set and URL encoding, readiness only after promotion, duplicate and stale requests, the cancellation join during a transfer and during promotion, each failure followed by a retry, an interrupted staging area after a restart, and navigation during a download. They do not connect to the network; the default `URLSession` loader and a device download remain manual checks.

Issue #192 adds `ModelLibraryRuntimeTests`. Five fake adapters for the iOS demo IDs and one demo without an adapter are registered over two fixture models, a `ManagedModelStore` in a temporary directory, and a fake transport serving a small EmbeddingGemma 2 fixture bundle. The fakes count previews, contents, explicit starts, gate rejections, runtime loads, stops, and saves, and can hold or fail a stop. The tests cover browsing and download completion without side effects, stale and forged gates, stops pending acknowledgement, variant changes and deletion, failed stops and retries, concurrent stops of one session, going back while a lease is being taken, a content appearance while a stopped session is being released, a start before the lease is verified, a resource deleted by another owner before the lease, a scene whose library store is released, transient and repeated stop failures after that release, a content appearance after its owner was abandoned, retained inputs and saves, scene phases, and two owners sharing one store. SwiftUI rendering, real demos, and devices are outside these tests.

Issue #198 adds `ModelLibraryAssemblyTests`. They build `ModelLibraryAssembly` from the real `IOSDemoCatalog` with five fake adapters that carry its demo IDs, a `ManagedModelStore` in a temporary directory, a transport that counts requests, and two legacy folders as migration candidates. They cover the registered demos and the library environment; refresh, browsing, previews, and download requests of the unconfigured artifacts (no session, no adapter content or work, no request, no managed folder, and unchanged legacy folders); and direct operations with another owner's ticket, an artifact that was never acquired, and a session that is stopping or stopped (no lease and no adapter work). A third test covers `ModelLibrarySelfTest`, the report behind `--model-library-selftest` ([iOS UI](model-library-ui.md#regular-ios-launch)). The app's own adapters are checked by the precondition in `IOSModelLibraryAssembly.make(catalog:)` and by that self-test on a device; the device checks are listed in the [integration record](validation/ios-models-integration-20261018.md).

The test fixtures use `owner/fixture` with fixed revisions and checksums. They are test inputs, not real distributions. `IOSDemoCatalog` remains unconfigured, without files or revisions, until the distribution definitions are adopted.

The initial independent review of #171 found an inspection path that bypassed the missing/invalid distribution rule. Validation completion and the execution gate now reject that path, with regression cases for both missing metadata and an unpinned revision.
